# 中文表达规范

中文文字的用词标准。**适用范围是读者会看到的每一处**：代码注释、docstring、
markdown 文档、提交信息、PR 标题和正文、发给人读的通知文案，以及对话回答。
不是只在某一类地方注意。哪些文字算在内，见第一节。

下面的例子不绑定任何一个具体项目，整份可以拿到别的版本库去用。

行文标准参照中国官方文件的写法：陈述句，主谓宾齐全，一个名词只对应一个确定的
所指，不写形容感受的词。

判断方法只有一条：**读的人会不会停顿一下。** 需要先翻回英文、或者需要先猜一层
意思、或者不知道这个简称指什么，就换掉。

## 一、哪些文字归这份规范管

**分界线是这句话打给谁看、落在哪里,不是谁会读到它。**

**写中文**：代码注释、docstring、markdown 文档、提交信息、PR 标题和正文、对话
回答，以及**发给人读的通知正文**——告警和日报在聊天软件里单独成一条消息，写给
运维读，用词照这份规范。

**写英文**：程序跑起来打进终端和日志文件的字符串——异常消息、断言和 panic 的
文字、日志行、构建脚本的输出与失败原因、打包元数据里的说明。

理由是这些字符串落在哪里：它们和编译器、运行时、构建工具自己的输出并排在同一个
终端里，而那些全是英文。一句话中间换一次语言，读的人要在两套断句方式之间切一次；
搜的时候要先猜作者当时用的是哪一半；贴进 issue 里还要多解释一句。两种语言各自都
比夹着好。

最常见的错误形状是**半句自己写的中文、半句上游库原样带上来的英文**：前半句说
这是哪个文件、哪一列，后半句是底层库抛上来的原文。这种消息两头都读不顺，而且
它给出的定位信息越多，夹得越明显。

复查时先看两处，那是这类中文最集中的地方：**错误类型的 `Display` 或等价的消息
模板**，以及**打包元数据里的说明**。后一处最容易漏，因为它一个版本库只有两三行，
平时没有人打开那个文件。

**这一条不做成单元测试。** 规则本身一句话说得清：源码里的字符串字面量不出现
中日韩字符，注释和 docstring 除外。做成用例的代价和它管的事不相称——注释的写法
一种语言一个样（`#` 在 Nix 里是注释、在 Rust 里是属性起头，`//` 反过来），Python
那一侧还要用语法树分辨，因为 docstring 本身就是字符串字面量；再加一份「哪些路径
算发布代码」的清单和一组证明扫描器自己没坏的探针，两百行测试代码换一条一句话的
规范。用例该测的是代码的行为。

## 二、三问

每写完一段，对每个名词和动词各问一遍：

1. **这个名词是不是从英文译过来的？** 读的人第一次见到它能不能知道指什么？
2. **这个动词字面上真的在做这件事吗？** 是比喻就换成主谓宾：谁、在什么条件下、
   读了什么、写了什么、结果是什么。
3. **这个简称第一次出现时，读的人能不能知道它指什么？** 不能就写全称，或者
   干脆换成一句话。

## 三、不用的词，以及改成什么

下面四张表是**样本，不是规则**。规则是上面三问。表能查出来的只有重复犯过的词，
而新写的文字里出现的多数是新词。

### 1. 英文直译词

中文里没有这个既有说法，读者要先翻回英文才懂。

| 用过的词 | 原词 | 改成 |
|---|---|---|
| 扇出 | fan-out | 一个请求拆成多次调用；一个信号同时触发多个任务 |
| 在飞 | in-flight | 已经开始、还没结束的那些 |
| 渲染器 | renderer | 生成这个文件的函数 |
| 负载形状 | payload shape | 消息里有哪些字段、各是什么类型 |
| 幻数 | magic number | 没有说明来源的数字常量 |
| 厂商 | vendor | 上游 / 供应方 |
| 桩 | stub | 函数名和类型都定好、函数体只有一行「未实现」的函数 |
| 哨兵 | sentinel | 表示缺失的固定取值 |
| 夹具 | fixture | 测试数据 |
| 契约 | contract | 数据集定义 / 接口定义 |
| 平面 | plane | 侧（离线侧 / 在线侧） |
| 工厂 | factory | 说清调用它得到什么 |

**标识符不改。** 目录名 `tests/fixtures/`、类名、字段名都是代码，不是散文；
散文里提到它们时照写标识符。**英文一侧也不改**：`contract`、`factory`、
`fixture` 在英文里是固有说法，改掉反而要读的人多绕一层。

### 2. 比喻和拟人

把「具体发生了什么」换成了一个感觉，读的人无法据此判断对错。

| 用过的词 | 改成 |
|---|---|
| 尺子 | 检查手段 / 对照文件 |
| 梯子 | 四级拆分、第 2 级、四级都走完还差 64 条 |
| 水位 | 直接写那两个数 |
| 腐烂点 | 这项检查随时间失去作用的地方 |
| 静默死亡 | 反复失败、不再被触发，且没有任何告警 |
| 活路径 | 实际会执行到的代码路径 |
| 吞掉 / 吃掉 | 被 `except` 捕获后不再上报，计数按 0 算 |
| 咬人 | 读回筛不到行，于是每次重插一遍，而且不报错 |
| 抹平（历史） | 每个键只剩一行，时点历史不再存在 |
| 污染队列 | 它会让别人起的任务失败：抢到任务、抛不可重试的错、整个流程被标记失败 |
| 钉死 / 钉在 | 只允许一种取值；参数必须保持 4 个 |
| 守规矩 | 各自都没有超出配置的上限 |
| 不通气 | 进程之间不共享 |
| 红 / 绿 / 全绿 | 测试报错 / 测试通过 |
| 炸 / 必炸 | 直接写抛的是什么：`ImportError`、启动失败 |
| 收费（一次） | 这项工作只需要做一次 |
| 藏（在标识符里） | 那条检查读的是字符串字面量，类名是标识符，不在它的范围内 |
| 有话说 | 推送一条消息 |
| 响 / 才响 | 推送通知 |
| 一声不响 | 不推送任何消息；失败后只在界面上留下一条失败记录 |
| 长得一样 | 无法区分 |
| 淹掉 | 消息数量远超需要处理的数量 |
| 埋进 | 会混在里面分辨不出 |
| 悄悄变错 | 变错且不报错 |
| 划过去 | 读的人只会看其中一条，而未必是信息更多的那条 |
| 读起来像 | 与……无法区分 |

**名词也算比喻。** 给一个四级拆分起名叫「梯子」读起来生动，但这个名字不含级数、
不含顺序、不含「走完了没有」，而这三样正是要判断的东西。判断标准是：**这个词
含不含要判断的信息。**

**把代码写成会做事的一方，是这一类里最难自己发现的。** 判断方法比三问更直接：
**把句子的主语找出来。如果它是一段代码、一张表、一个分支或一个消息通道，而谓语
是人才做得出的动作（说、问、答、响、盯、埋、藏、收费），就要改。** 改法是换主语
（换回人，或换回具体机制），或者换谓语（换成推送、返回、记录、区分）。

**写的题目本身是「通知」的时候，最省事的动词全部是拟人的。** 上表最后十行会在
同一个改动里成片出现：表「有话说」、通道「响」、失败「一声不响」、两种状态
「长得一样」、消息「淹掉」频道、告警被「埋进」日报、结果「悄悄」变错。这不是
十个孤立的用词，是一整段行文都把程序当成了说话的一方，因为这个改动的主题就是
让程序说话。同一段里的英文（`send`、`say nothing`）不是问题，中文照着译过来才是。

### 3. 自造简称

比直译词更难发现：直译词至少能翻回英文，自造简称只有写的人知道它指什么。

| 用过的词 | 实际指的东西 | 改成 |
|---|---|---|
| 指纹 | 记录每个字段当前取值、用于比对的提交文件 | 字段对照文件，或直接写文件名 |
| 攻击 A / 攻击 B | 为验证测试有没有用而故意写进代码的错误改动，看完就撤销 | 验证用的改动 |
| 轴检查 | 某个适配器对不支持的分块单位抛错的那段代码 | 对分块单位的检查 |
| 真类 | 实际存在的异常类 | 实际存在的异常类 |
| 存活发现 | surviving findings 的直译，指先自己试着推翻、推翻不了才报上来的问题 | 查实的问题 |

规则：**第一次提到某个东西就写全称或文件名**，之后再用短的说法。

### 4. 学究气的书面词和口语俚语

| 用过的词 | 改成 |
|---|---|
| 判据 | 检查条件 |
| 背锅 / 翻车 / 踩坑 / 拉胯 | 直接说哪一步没做到什么 |
| 跑失败了 / 已跑完 | 本次执行失败 / 本次执行已完成 |
| 顺带把……降下来 | 并降低……的频率 |
| 一档一档 / 各降一档 | 各降低一档，写清从多少改到多少 |

## 四、照用的词

中文里已经站住的技术词不在此列：幂等、心跳、回补、探针、分块、重试、落地、
限流、去重、回填、快照。

## 五、检查顺序

写完回头逐句读一遍。**顺序是：先标题、小标题和一句话的提交信息主题，再正文。**

标题是最短、最后写、也最像随口说一句的那一处，而它恰恰是评审第一眼看到的。
「写完检查一遍，标题一起检查」这句话写下之后，仍然会只检查正文。

**一处也要改，因为位置比次数重要。** 一个词在仓库里出现 1 处还是 100 处，
和该不该改无关；它出现在哪里才相关。README 第一句是**唯一一句所有人都会读**的
话，也是最容易被整句搬走的一句——仓库简介、项目列表、对外介绍都会照抄它，而这些
位置不在任何一次 grep 的范围里。所以检查存量时，README 第一句和仓库简介要一起看。

## 六、这份规范失效的六种方式

每一条都是在规则已经写下、并且已经改过几轮之后仍然发生的。

**1. 拿词表当检查清单。** 对着三张表 grep 一遍、一个词都没命中，于是认为查过了；
而同一篇里有一批表里没有的新词。表的左列是**样本**，规则是三问。

**2. 拿仓里已有的写法当豁免依据。** 被指出某个词不规范时，第一反应是「别的文件里
也这么写，属于既有用法」。左列的收录标准恰恰是「本仓真实出现过并被指出的」——
**出现过是收录的理由，不是豁免的理由**。同一个词在别处出现过，只说明那里也要改。

**3. 给直译词加一段定义，当成已经改了。** 有人问「这个词什么意思」，于是在它第一次
出现的地方补一段定义——他接着问「这种词怎么还存在」。加定义是**自造简称**那一类的
改法；直译词的改法是**换掉这个词**。换掉之后往往不需要定义也读得懂，那段定义随之
只留下真正的内容。

**4. 以为「中文里查得到这个说法」就等于它站住了。** 一个译法能查到用例、甚至有
三十年的固定译法，仍然可能要改。判断依据是上面三问，不是有没有人这么说过。
**一个英文词有两个并存的中文译名，本身就是它还没有站住的证据**——同一个词，官方
文档一种译法、社区另一种译法，说明读的人也在两者之间犹豫。对照〈照用的词〉那一类：
幂等、心跳、回补，今天的中文里都还在用，用的也是同一个意思。

**5. 以为「同一个译名在别的领域站得住」就等于在这里站得住。** 这一条比上一条难
发现：词表 grep 不出来，上网也查得到用例。上一条是**一个英文词对应两个中文译名**，
这一条是反过来的**同一个中文译名对应两个不相干的所指**。能问出它的是第一问：
现代汉语里这个词，读的人的第一反应是什么。

**6. 新造的术语没有第二个读者。** 一个词用得越顺手，越说明只有写的人读过它。
写的人每次都知道自己在说什么，而**写的人读不出自己的停顿**。所以新起一个模块、
新起一个仓库的时候，**第一批被造出来的术语要单独检查一遍**——那批词后面会被引用
几十次，而它们诞生时通常没有第二个读者。越是中心的那个名词，被复述的次数越多，
而它恰恰是最没有机会被第二个人读到的那一个。

## 七、英文 docstring 里的比喻要一起改

否则写中文时会照着译回来：英文 docstring 里写了 ladder，中文就跟着用了「梯子」。

一起改的英文比喻包括 swallow（改成说明被 `except` 捕获后如何计数）、ruler
（改成具体的检查名）、sibling（改成 another upstream）、push back（改成 refuses
a request）、blow through（改成 far past）。

判断标准和中文一侧相同：这个词含不含要判断的信息。

## 八、改动生成文件里的字符串时

要改的词写在**生成文档的那个函数**里时，改完必须重新生成一次，手改生成出来的
文件会让「检查产物是否最新」那一步报错。同样地，有些说明文字是作为数据写在定义
里的（备注、缺口说明、开头的介绍段），最后进入生成的文档，改完也要重新生成。
