# NixOS 根盘迁移

把一台运行中的 NixOS 主机的根文件系统搬到另一块盘，全程保留旧盘作后备。
下面的数字来自 2026-08-27 的一次实施：931G 的 NVMe 换成 1.8T 的，搬了 727 GB、
1096 万个文件，停机约 20 分钟。

本文记录做法和**踩过的三个坑**。坑的部分比步骤更值得读——步骤在
[NixOS Wiki](https://nixos.wiki/wiki/Storage_optimization) 上就有，而这三个坑都不会
在出错的当下报错。

## 总体思路

**全程是复制，不是移动。** 旧盘从头到尾不动，新盘起不来就切回去，什么都没丢。
这个性质决定了整个流程可以在生产机上做，也决定了失败的代价只是时间。

```
分区格式化 → 在线 rsync（服务照跑）→ 停服务补增量 → 在新根里重建一代 → 装引导 → 重启
```

停机窗口只有「停服务补增量」到「重启」这一段。第一遍在线跑是因为 `/nix/store`
占了 86% 且内容不可变，可以边跑边拷。

## 步骤

### 1. 分区

```bash
printf 'label: gpt\nsize=1GiB, type=uefi, name=ESP\ntype=linux, name=nixos\n' \
  | sudo sfdisk --wipe always /dev/nvme0n1
sudo mkfs.fat -F32 -n BOOT /dev/nvme0n1p1
sudo mkfs.ext4 -F -L nixos /dev/nvme0n1p2
```

ESP 给 1 GiB。原来那块是 512 MB，NixOS 多留几代内核时会满。

### 2. rsync

```bash
sudo mount /dev/nvme0n1p2 /mnt/newroot
sudo mkdir -p /mnt/newroot/boot && sudo mount /dev/nvme0n1p1 /mnt/newroot/boot

sudo rsync -aHAXxS --numeric-ids --info=progress2 \
  --exclude='/tmp/*' --exclude='/var/tmp/*' --exclude='/mnt/*' \
  --exclude='/lost+found' \
  / /mnt/newroot/
```

参数逐个说：

| 参数 | 为什么 |
|---|---|
| `-H` | `nix-store --optimise` 用硬链接去重，不带它拷过去会膨胀。注意 `-a` **不含** `-H` |
| `-A -X` | ACL 和扩展属性，`-a` 同样不含 |
| `-S` | 稀疏文件。Docker 镜像和虚拟磁盘会中招，一个 10G 的稀疏文件能拷成 100G |
| `-x` | 不跨文件系统。`/proc` `/sys` `/dev` `/run`、Docker 的 overlay、NFS 挂载都会自动跳过，只留空的挂载点目录 |
| `--numeric-ids` | 按数字 UID/GID 传，不查名字表 |

**检验硬链接和稀疏文件有没有出问题，看目标和源的用量是否接近**：这次是 727G 对
726G，两个风险都没发生。

第二遍在停服务之后跑，加 `--delete`，速度快 800 倍（只传改动）。

### 3. 停服务，尤其是 nix-daemon

先停掉一切会写盘的东西——数据库、容器运行时、自己的常驻服务。会写的东西可以用
这条列出来：

```bash
systemctl list-units --type=service --state=running
```

然后停 `nix-daemon`，**socket 要先于 service**：

```bash
sudo systemctl stop nix-daemon.socket nix-daemon.service
```

只停 service 的话 socket 会立刻把它拉起来，于是 `/nix/var/nix/db/db.sqlite` 仍然在
被写，拷过去可能是事务中间态。数据库坏了不会当场报错，但 nix 从此不知道哪些路径
存在，**下一次垃圾回收会把没登记的路径删掉**。

### 4. 改配置

**不要重新跑 `nixos-generate-config`。** 手工改 `hardware-configuration.nix` 里的两个
UUID，用 `blkid` 直读取值：

```bash
sudo blkid -s UUID -o value /dev/nvme0n1p2
```

### 5. 在新根里重建，然后装引导

```bash
sudo nixos-enter --root /mnt/newroot -- nixos-rebuild boot --install-bootloader
```

`--install-bootloader` 会往 `/mnt/newroot/boot`（也就是新盘的 ESP）写 systemd-boot，
碰不到旧盘。`canTouchEfiVariables = true` 时它同时会在 UEFI 的 NVRAM 里建一个指向
新盘的启动项。

### 6. 重启

```bash
sudo efibootmgr -n 0001      # BootNext，一次性
sudo systemctl reboot
```

`BootNext` 是一次性的，UEFI 在尝试之前就把它删掉。所以新盘起不来时，断电重启会自动
回到 `BootOrder` 指定的旧盘，不需要进 BIOS。

## 三个坑

### 坑一：只装引导不重建，会得到「引导在新盘、根在旧盘」

**NixOS 把根分区的 UUID 编译进 stage-1 启动脚本。** 现有的那一代是用旧盘 UUID 构建
的，只把它的引导装到新盘，开机时引导器从新盘加载、stage-1 却去找旧盘的 UUID——**而
旧盘还插在机器里，找得到**。

于是系统从新盘引导、挂载旧盘作根，两块盘都能读写，**看起来一切正常**，数据从此分叉。

所以第 5 步是 `nixos-rebuild boot`，不是 `switch-to-configuration boot`。

验证办法是读新一代的 `initrd-fsinfo`：

```bash
$ cat /nix/store/…-initrd-fsinfo
/
/dev/disk/by-uuid/e303f153-45d0-456b-a55b-92178006e444
ext4
x-initrd.mount,noatime
```

### 坑二：重建之后再跑一次 `rsync --delete`，会把那一代删掉

这是本次失败两回的原因。

新建的那一代**只存在于新盘上**（它是在 chroot 里构建的），而 `--delete` 的语义是
「目标上源没有的东西删掉」。所以重建之后再同步一次，那个系统闭包和整个
`/nix/var/nix/profiles/` 都会被删回旧盘的状态。

ESP 不受影响（`-x` 不跨文件系统），引导器、内核、initrd 都还在，UUID 也还是对的。
于是开机时 stage-1 **挂上了根，却找不到 `init=/nix/store/…/init`**，报的是这一句：

```
An error occurred in stage 1 of the boot process, which must mount the
root file system on '/mnt-root' then start stage 2.
```

这句话是 stage-1 任何一种失败的通用提示，看不出具体原因。真正的原因在它**上面几行**。
机器前可以按 `i` 进 initrd 的 shell 查：

```sh
blkid | grep <新盘 UUID>        # 设备认不认得
ls /mnt-root/nix/store | head  # 根挂上了没有
```

**修正是顺序：重建必须是最后一个写新盘的动作。**

### 坑三：`nixos-generate-config` 会写错 UUID

[NixOS/nixpkgs#62444](https://github.com/NixOS/nixpkgs/issues/62444)：它读
`/dev/disk/by-uuid` 的符号链接缓存，而不是 `blkid`。`mkfs` 之后那里可能还是旧值，
于是一个**不存在的 UUID** 被写进配置，机器起不来。

所以手工改，并把理由写进文件头——否则下一个人看到「Do not modify this file! It was
generated by nixos-generate-config」会照着重新生成。

## 验证清单

重启后逐项核对，任何一项不符都不要继续：

```bash
findmnt -no SOURCE,UUID,OPTIONS /     # 设备、UUID、noatime
df -hT /                              # 容量确实变大了
efibootmgr | grep BootCurrent         # 从哪个条目启的
nix-store --verify                    # 数据库与 store 一致
systemctl list-units --state=failed   # 应为 0
```

**重建之后还要单独验一次「ESP 条目指向的 `init=` 路径在盘上真的存在」**：

```bash
gen=$(sed -n 's/^default //p' /boot/loader/loader.conf)
init=$(grep -oE 'init=/nix/store/[^ ]+' "/boot/loader/entries/$gen" | sed 's/^init=//')
[ -x "$init" ] && echo OK || echo "指向了不存在的路径"
```

坑二就是从这里漏过去的。当时验的是「条目指向的闭包和 profile 一致」，在重建的当下
成立，同步把它删掉之后就不成立了。**验证要放在最后一次改动之后，不是改动的当下。**

---

## 迁移之后

**旧盘上留着一份完整可启动的系统副本**，固件的启动菜单里也还有它的 ESP。启错了机器
照常起来、看上去一切正常，但写入全落在旧盘上，两份副本无声地分叉。

确认新盘稳定之前不要动旧盘——它是后备。确认之后，要么清掉它的 ESP，要么明确记住当前
启的是哪一块。
